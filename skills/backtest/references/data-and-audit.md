# 数据、时点与最低回测审计

## 日期与可用信息

| 层 | 日期边界 |
| --- | --- |
| Scheme 表单/分析参数、`Universe.query(start,end)` | `[start,end)`，end 不包含 |
| `scheme.data.query` 的 Runtime 字典 | `start_date/end_date` 闭区间 |
| Scheme 引擎适配 | 把 end 转成 `end - 1 天`，只转换一次 |
| 原生 Backtest config / `run()` | `startDate/endDate` 包含结束日 |
| `load_messages(start,end)` | `[start,end)`；批次跨度不是决策频率 |

明确交易所时间语义、实际时间戳粒度与排序；无时区的中国股票时间不当成 UTC 二次转换。开盘决策不能读取当日收盘/high/low，已完成前一日窗口也不需要机械再 shift。收盘信号是否只能下一交易日执行，需要结合当前组件队列、执行窗口和插件实测，不从回调名称猜成交时点。

Solo 查询本身不自动提供 Arena 历史 helper 的严格日期隔离；Algo 必须限制查询结束日期与发布可用时间。负 shift、未来收益标签及全区间计算误用会前视；供应商修订、财务公告、成员填充、复权基准与数据快照版本是独立 PIT 检查。

## 数据域、成员与退出

- `Universe` 单次执行注入 `Universe.member`、`codes=[]` 的 `dataset_query`，不做本地 `codes_query` 预选、不默认加入 filters。`scheme.data.query` 是本地直接执行包装，不是 Runtime alias；每进程首次空 `codes` 从 CoreData 全历史所有记录取 distinct codes 缓存为 tuple，后续复用，不按日期或 `close` 重建，显式 `codes` 原样保留。
- 明确决策使用当前可知成员还是前一完成截面的成员；数据在当天存在不证明盘前已可用。CS 参与域的 `on` 与最终删行 `filters` 分开。
- `evaluate(start,end)` 返回交易日×固定证券域的 BOOL 面板，非成员和缺失成员为 False；当日或整个区间无成分也保留全 False，不因缺行情缩列。交易日轴仍按请求区间内真实 `close` 日期确定。
- 行情加载范围与选股范围不同。保留退出/失效股票的交易与估值数据，显式 `symbols` 也要覆盖需要退出的持仓。
- 目标删除、信号为空不等于持仓卖出；检查报价、停牌/缺价、可卖数量、涨跌停、资金和活动订单。
- 本地请求 `codes=[]` 使用进程固定全市场域，不是“没有标的”。业务候选为空时不要据此发起全市场价格查询；已有 `evaluate` 面板的全 False 日直接按无成员处理，明确空信号且仍审计原持仓退出。

## Solo 行情和价格尺度

当前 Scheme `stock_daily` 从查询结果生成 09:30 open / 15:00 close 单档快照，数量近似十亿股；不表达盘中路径、真实容量、排队或市场冲击。当前封装要求 `open/close/pre_close/up_limit/down_limit` 有效；不会套 Arena 的 high/low 推测涨跌停价。实际字段、缺失、NaN/非有限值与非正价格先查，不能用均价或最近估值偷偷回填。

`stock_snapshot` 使用真实五档原价与日线参考价；不要假定 Arena 的分钟 helper、报价缓存、无效数据处理或完整区间覆盖检查也存在于 Solo。按实际 loader/schema 检查报价覆盖、参考价、单边盘口和部分成交。

分别记录查询价格、成交价格、估值价格、分红除权/复权因子、基准与费率。Solo 没有因为使用 Arena 数据就自动应用 Arena 的 `adj` 或补价逻辑；手动 `close * adj_factor` 也只调整那个计算，不能宣称执行账户已经同尺度或获得分红补偿。确认实际 T+1、延时、整手、首次建仓下限与最低费设置，不把市场常识当成已启用配置。

## 订单、成交与空对象

| 状态 | 含义 | 终态 |
| ---: | --- | --- |
| 4 | 已报 | 否 |
| 0 | 部分成交 | 否 |
| 1 | 全部成交 | 是 |
| 2 | 撤单成功 | 是 |
| -1 | 审批/风控拒绝 | 是 |
| -2 | 撤单拒绝，原单仍可能活动 | 否 |
| -3 | 日终/结束时未成交失效 | 是 |

对每批 orders/trades 全部遍历。`OrderReport.tradeQty` 通常累计，撤单成功时可表示撤销量；`TradeReport.tradeQty` 是当次成交、`totalVolume` 是累计。不要把不同形式混合求和。`-3` 可能仅在最终结果表出现，不能保证收到对应回调；`-2` 后重新核对活动订单。

先减仓再增仓时，等待实际成交/资金更新，为费用和价格变化留余量；未成交部分不能重复再下同目标。空持仓按真实接口处理为空字典/表，不能直接对 NULL 求和或认定“清仓成功”。现金是可用现金，不一定等于权益，也不能把持仓均价当现价。

## 四张业务表与额外诊断

先检查实际 report/文件列表、schema、日期、重复键、代码与有效数值，不假定文件名已经证明数据正确。

| 表 | 粒度与核验 |
| --- | --- |
| `trade_details` | 订单状态事件；按 orderId 还原生命周期，事件行数与唯一订单数分报 |
| `daily_trading_statistics` | 证券×日实际成交；按 direction 核对买开/卖平等量、额、均价 |
| `daily_positions` | 证券×日盘后持仓；零仓行可能存在/缺失，检查无法退出与期末仓位 |
| `daily_portfolios` | 日账户记录；检查资金、市值、权益、净值、PnL、收益、累计费用 |
| `allocation_diagnostics`（Solo） | 分配方法/失败原因；辅助解释，不能代替交易账户审计 |

订单事件不是纯成交表：不对全部行的 `tradeQty` 求和；终态为 `{1,2,-1,-3}`，不按状态码最大值取“最终状态”。没有稳定序号且同刻事件冲突时，披露排序证据不足。用成交回报/方向交易统计交叉核对，再解释事件累计字段。拒单原因仅在真实 `orderInfo` 或日志提供时解释，不合成不存在的结构化原因。

持仓表 `todaySellVolume/Value` 在 Arena 文档的插件版本有已知可靠性限制；当前部署需复测，卖出至少用 `daily_trading_statistics` 与订单方向交叉验证。`closePrice` 可能是沿用估值，不能证明当日有可交易报价。

## 账务与收益

按日期排序并使用浮点容差；在字段语义与现金流条件满足时检查：

```text
权益 ≈ 现金 + 持仓市值
净值 ≈ 权益 / 初始资金；累计收益 ≈ 净值 - 1
totalPnl ≈ floatingPnl + realizedPnl
日收益 ≈ 当日净值 / 前一有效日净值 - 1
日费用 = 当日累计费用 - 前一有效日累计费用
方向均价 ≈ 方向成交额 / 方向成交量（成交量 > 0）
```

首行前值用初始资金、净值 1、累计费用 0。费用已进入现金/权益，不重复扣减；公司行为、冻结资金、入出金与初始持仓单独按账户语义对账。文档基线插件 `setPosition` 存在初始费用不完整进入 totalFee/totalPnl 的问题，不把异常差额重复扣费或伪造成交。

缺失、NULL、0 与无成交缺行分开；不能把缺失收益一律填 0 后宣称绩效有效。空账户结果不输出有效年化。明确收益频率、年交易日、无风险率、波动/ddof、首日回撤和基准日期；不要照搬 Arena Backend 指标公式为 Solo 保证。期末持仓、活动订单、拒单、撤单拒绝、部分成交和失效分别披露，封装不自动代表已平仓。

最终结论覆盖收益、资金、持仓、实际成交/订单终态、拒单五方面，并说明价格/PIT/撮合与数据覆盖限制。完成、编译通过、净值上涨或日志显示订单号，都不等于这些审计已通过。
